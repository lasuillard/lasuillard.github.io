기술 블로그를 작년 말에 Railway로 옮겼습니다. 블로그를 Django로 완전히 재작성하고 필요한 동적 기능들을 붙이기 위해서였죠. 하지만 최근 다시 GitHub Pages로 블로그를 옮기게 되었습니다.

## 🤔 전환 이유

첫 번째 이유는 서버 필요성 감소입니다. 블로그를 Django로 다시 만들었던 데에는 다음과 같은 목적이 있었습니다.

- 유지보수 자동화

  정적 웹사이트로는 할 수 없는 동적 기능을 비롯해 Celery와 Beat 기반 비동기 작업을 중심으로 한 다양한 유지보수 및 자동화 작업 구현 및 관리를 계획했습니다.

- 다양한 동적 기능 구현

  처음에는 개인 블로그를 개인 홈페이지로 만들어 이력서, 연관 프로젝트 및 블로그 글 등을 총망라해 관리하고자 했습니다.

- Django 학습

  Django SSR을 활용하여 웹 애플리케이션을 개발, 배포, 운영해보는 경험을 쌓고 싶었습니다.

하지만 블로그를 운영하면서 이러한 구성이 제 블로그 운영 및 관리 패턴과 다소 동떨어져 있다는 사실을 체감했습니다. 작업 스케줄링은 Celery 대신 Railway Functions와 Cron 기능을 활용하는 것으로 충분함을 알게 되었고, 블로그 글이나 이력서, 포트폴리오 등을 위해 다양한 Django 앱을 개발하고 관리하는 것은 그리 편리하지 않았습니다.

두 번째 이유는 비용입니다. 지난 10개월 간 지출한 $55.95가 효용성 대비 합리적이지 못했다고 판단했습니다. 블로그 사용 및 관리 패턴을 감안했을 때, 정적 웹 사이트 호스팅 대비 크게 나은 점이 없었다는 것이죠.

![Railway 결제 내역](./assets/railway-billing-history.png)

여전히 Railway의 비용 정책은 매력적입니다. Railway Hobby 플랜은 월 $5에 불과한데다 실제 CPU 및 메모리 사용량에 기반하는 과금 정책, 그리고 서버리스 기능을 활용한 개발 환경 비용 절감 덕분에 월 $5 ~ $6 정도로 Django와 Postgres, Redis 그리고 Celery로 구성된 제 블로그를 개발과 운영, 2개 환경에서 큰 문제 없이 운영할 수 있었으니까요.

결국 블로그를 Django로 전환한 것이 제 기술적 허영심과 과욕, 섣부른 판단이 부른 실수였음을 받아들여야 했습니다. 그리고 다시 GitHub Pages로 돌아가기로 했습니다.

## 🏗️ 전환 과정

기존 정적 블로그 코드 저장소는 아카이브 상태로 보존된 상태였기에 쉽게 코드를 복원할 수 있었습니다. 하지만 그 짧은 기간 동안, 많은 패키지 업데이트가 있었고 제 개발 방식도 많이 달라져 있었습니다.

### 🛠️ 개발 환경 최신화

겨우 10개월도 채 안 되었지만 패키지 버전이 많이 뒤처져 있었습니다. 주요 프레임워크 및 라이브러리의 메이저 버전 업그레이드, 보안 패치 등이 쌓여 있었죠.

- 개발 환경 변경

  최근 프로젝트와 비슷하게 개발 환경을 최신화했습니다. 개발 컨테이너에 크게 의존하는 기존 구성 대신, Nix를 활용하여 프로젝트 도구를 관리하면서 더 단순화된 개발 환경으로 전환했습니다.

- 불필요한 구성 삭제

  Lighthouse를 비롯해 사용되지 않는 워크플로와 개인화된 GitHub Copilot 설정, Dependabot 설정 등 더 이상 사용하지 않는 구성 요소들을 과감히 삭제했습니다.

- SvelteKit 어댑터 변경

  정적 웹 사이트로 빌드하기 위해 어댑터를 [adapter-static](https://svelte.dev/docs/kit/adapter-static)로 변경했습니다. 어댑터 변경은 사이트가 빌드되는 방식을 바꾸기 때문에 필연적으로 구현 변경 및 버그 수정이 뒤따랐습니다.

  이 과정에서 기존에 작성해 두었던 단위 및 E2E 자동화 테스트가 큰 도움이 되었습니다. 로직 문제를 빠르게 식별하고 수정할 수 있었고, 스크린샷 스냅샷을 통해 웹 사이트 변경을 손쉽게 찾아낼 수 있었습니다.

### 🚀 GitHub Pages 배포 구성

Django로 블로그를 재작성하기 전, Cloudflare Workers로 배포 환경을 전환했던 적이 있습니다. 이 과정에서 GitHub Pages 배포 구성이 삭제되었기 때문에 다시 워크플로를 작성해야 했습니다.

### 🚚 블로그 글 이전

최근 블로그 글들은 Django 모델로 관리되고 있었기에 이를 다시 정적 파일로 변환해야 했습니다. 기존 글들을 Markdown으로 변환하고, 필요한 메타데이터를 추가했습니다. CloudFront에 의해 서빙되던 이미지 등 애셋 또한 로컬에 저장해 참조하도록 했습니다.

### ↪️ 도메인 전환

현재 블로그 도메인(`lasuillard.me`) 트래픽을 옛 도메인(`lasuillard.github.io`)으로 전환할 필요가 있었습니다. 링크를 통해 이전 블로그를 접속하더라도 새 블로그로 문제 없이 접속할 수 있도록 말이죠.

하지만 Railway에 리디렉션 서버를 띄워둔다면 당분간 추가 지출이 발생할 터였습니다. 가능한 가장 쉽고 확실한 방법을 찾던 중, 도메인을 관리하고 있던 Cloudflare의 [Bulk Redirects](https://developers.cloudflare.com/rules/url-forwarding/bulk-redirects/) 기능에 대해 접하게 되었습니다.

![Cloudflare Bulk Redirects](./assets/cloudflare-bulk-redirects.png)

기존 Django 블로그는 I18n 기능을 포함하고 있어 URL 경로가 다양(`/blog`, `/ko/blog`, `/en/blog`, ...)했습니다. 제 블로그는 글 수가 많지 않아서 경로 접두사까지 처리하는 리디렉션 규칙을 처리하는 복잡한 리디렉션 규칙을 작성하는 대신, 리디렉션 URL을 하나하나 직접 입력해주었습니다.

리디렉션 목록을 CSV 파일로 업로드할 수도 있으니 큰 웹사이트라면 스크립트를 통해 CSV 파일을 만들어 업로드해도 좋겠습니다.

## 📝 후기

다시금 전환을 결심하게 된 데에는 최근 AWS 자격증을 취득하기 위해 공부한 영향이 크다고 생각합니다. 공부 과정에서 비용, 보안, 유지보수성 등 다양한 요구사항을 만족하는 최적의 아키텍처에 대해 많이 고민하게 되었고, 다시 한번 블로그의 요구사항과 현재 아키텍처에 대해 제고하기에 이르렀다고 봅니다.

기존 Django 블로그는 구성과 용도를 바꿔 재활용하려고 합니다. Celery를 쳐내고 서버리스 환경에서 최저한의 비용으로 동작할 수 있는 유용한 개인용 웹 애플리케이션을 만들어볼 생각입니다.
